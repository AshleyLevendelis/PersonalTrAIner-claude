- [x] **THE COACH IS TOLD WHAT ACTUALLY HAPPENED — BUILT 9 Oct 2026 (tester's H23, the context
  half of H8 and of H22's first incident).**
  **WHAT WAS WRONG.** Reproduced first: the header the app itself writes for the coach, given a
  session closed at 7 of 9 sets, printed *"…and it is ALREADY DONE — finished and logged. There
  is nothing left to train today."* `finished` meant only "the session was closed". "Sets logged"
  was the number of ROWS in the log — warm-ups and added exercises included — against the plan's
  count, so nine rows of which six were planned working sets read as 9 of 9. Beside that header
  the coach had today's full plan row and a 14-day log, and no join between them; asked for a
  recap, it listed the untouched exercise as work. Three more things it was never told: that a
  day had been swapped for football, rested on purpose or missed (the week strip's hook handed
  those over and the row builder read none of them); that a lifting day already carries a
  prescribed finisher; and how any earlier request ENDED — a card's text in the history is "Want
  me to …?" for ever and a refusal is an ordinary sentence, which is how Thursday's refused
  salmon request came back as a dinner card on Friday.
  **WHAT IS BUILT.** All of it is app-authored context assembled in the frontend
  (`chat-plan-context.ts` and `ChatAssistant`'s context builder) and interpolated verbatim by the
  deployed function, so it reaches the coach on a frontend push.
  - **Header.** "ALREADY DONE" only when every planned set is in the log. Otherwise: *"They
    CLOSED the session with 6 of 9 planned sets logged. NOT LOGGED: Band Tricep Kickback (0 of
    3). Nothing more is owed today, and the sets that are not logged were not recorded as done."*
    The count is working sets on PLANNED exercises, through the Exercise tab's own set reader,
    capped per exercise so a fourth set on one lift cannot cover a missing set on another.
  - **"TODAY, EXERCISE BY EXERCISE"** under the header: each planned exercise with logged against
    planned and the sets themselves, anything logged that was not on the plan, the finisher, and
    today's cardio in the cardio history's own words (it reads today's line from the cardio
    reader builder X1 merged in round 1, so one walk is never worded two ways). Shown once
    something is logged or the session is closed. An empty plan still yields exactly `''`.
  - **Week rows say what happened to the day:** closed with work logged / part-done / "NOT DONE
    AS PLANNED — they did Football · 60 min · Hard instead, and said so" / rested on purpose /
    "MISSED — they said so" / "NOTHING LOGGED — the day has passed". Today's own row carries no
    tag; the header and the block say today exactly.
  - **A lifting day's row names its finisher** and its optional mobility.
  - **Every assistant turn in the history says how its request ended:** `[OPEN: …]`, or `[CLOSED:
    they tapped Apply…]`, `[CLOSED: they declined this…]`, `[CLOSED: this offer timed out
    unanswered…]`, `[CLOSED: the app tried and could not apply this…]`, `[CLOSED: the app could
    not do this…]`. A card nobody tapped reads as closed once its window has passed. Facts, not
    instructions — the same rule the header keeps.
  **DECIDED AS A CSCS COACH, basis:** unlogged planned work is reported as **"NOT LOGGED"**,
  never "skipped". The app knows it holds no record; it does not know the work was not done
  (people train off their phone), and the coach's own rule is that the person's memory outranks
  the list. And a past closed session is "closed — work was logged that day", not "done": the
  strip's state means the session was finished with something in it, not that every set was.
  Nothing here changes a prescription, so the five-question review has nothing to answer beyond
  "in scope".
  **VERIFIED.** `test:coach-happened` — new, pure, about two seconds (55 checks). 26 mutations:
  25 caught. The one miss was a name-fallback that the shared set reader already performs — a
  second mechanism for one property, so it was deleted rather than given a check. `verify:
  moved-edit` §10 reads the request a real chat mount sends after one card is applied and one
  declined: both arrive marked CLOSED, neither arrives bare. **That driver found a real defect no
  source check had:** a confirmed card's view is replaced by its receipt, which dropped the
  outcome — the applied change went out as an unanswered question. Fixed here.
  **RE-ANCHORED, deliberately:** `test:coach-clock` pinned the literal `stampTurnTime(m.content`;
  the content now passes through the outcome stamp first. It holds the same property (the history
  map stamps each turn with its own content and time on the app clock); 1 mutation, caught.
  **NOT VERIFIED, and PARTIAL.**
  - The today-by-exercise block on a real mount (logic and source wiring only).
  - **Outcomes survive a reload on the same phone only.** They are carried across the history
    re-read by message id from this phone's cache. A different device, or a cleared cache, sees
    the turns unstamped again. The durable version writes the outcome into
    `chat_messages.action_data` (an existing column, no migration) — not built.
  - A refusal is marked closed only when it is the app declining to build a card. A refusal the
    MODEL words itself is not marked.
  - Whether the model READS any of this is the coach exam's to grade. The exam was not run (no
    credentials here), and an exam case for "recap after a part-done session" is not written.

- [x] **A MOVED SESSION CAN BE EDITED, FROM ITS OWN SCREEN AND FROM THE COACH — BUILT 9 Oct 2026
  (tester's H15, H19; the "I'm wiped" symptom of M26; the third H22 incident's wrong sentence).**
  **WHAT WAS WRONG.** Reproduced first with the app's own functions (`test:session-ref` §1):
  after Monday's session was moved to Friday every screen that SHOWS Friday resolved it through
  `sessionForDate`, and every EDIT was addressed by the weekday being looked at — whose own plan
  row is empty. Hence, verbatim: "Friday is a rest day — there's nothing on it to swap.",
  "There's no session on Friday to shorten.", "I couldn't find that exercise on that day." The
  on-screen swap was worse: the editor hands back the same plan when the slot does not exist,
  and the handler saved that unchanged week, cleared the error and closed the dialog as if it had
  worked. About twenty call sites carried the same substitution.
  **WHAT IS BUILT.** One resolver output — a session reference (`src/lib/session-ref.ts`): the
  date being looked at, **the plan row the session lives in** (the only key an edit may write
  to), and **the weekday to SAY**. It is built from the same seven cells the week strip is drawn
  from. Every edit takes it:
  - **Exercise tab:** take out, shorten, lighter, rebuild, move up/down, add (with its price and
    its impact), swap from today's card, swap from a peeked day, add a cardio session, and the
    shorten times offered in "What happened?".
  - **Programme view:** swap. **Tools tab:** today's conditioning timer.
  - **Coach, client half:** swap, add, remove, reorder, shorten, rebuild, volume, cardio session,
    and the plan names and set counts used when logging sets by chat.
  **Sentences name the day on screen.** Sam's moved session has three exercises, so once the
  lookup works "Drop it" meets the never-below-three floor — and that refusal reads *"That would
  leave Friday with fewer than 3 exercises. Take the whole day off instead, or swap this one for
  something easier."*, in the same change. Coach cards and the receipts after them say the
  on-screen day too. One place reconciles the two names (`sayDayIn`), so no edit had to learn
  about moves and no sentence can be forgotten.
  **Days swapped for another activity, rested on purpose or marked missed go through the same
  lookup** and are refused in a sentence: their plan row still holds a full session, and an edit
  would rewrite work the person has said they are not doing. Logged work outranks the flag, as
  the week strip already ranks it (said football, lifted anyway → editable). A past day that
  only LOOKS missed is still editable, as it was.
  **A swap that changes nothing now says so** — "That swap didn't go through — nothing has
  changed. Try it again from the exercise's menu." — instead of saving the same week and closing.
  **DECIDED, AND BY WHOM.**
  - Mechanical: which row an edit writes to has a right answer.
  - **Decided unprompted, reversible — words, so Ashley's to change:** the four new refusals
    ("{Day}'s session is on {Other} this week, so there's nothing on {Day} to change." / "{Day} is
    down as {activity} instead of your session, so there's nothing on it to change." / "{Day} is
    down as a rest day you chose, so there's no session on it to change." / "{Day}'s session is
    down as missed, so there's nothing on it to change."), and the "didn't go through" sentence.
  - **Decided unprompted, reversible:** "Monday" said to the coach after Monday's session moved
    to Friday means that SESSION, wherever it now is — except for a cardio session, which is
    about the calendar day and is refused on the emptied Monday in the first sentence above.
  **CSCS REVIEW.** 1. Training effect: none of its own — the same edits run, on the session the
  person is actually doing instead of on nothing. 2. What it takes away: an edit on a day marked
  swapped / rested / missed is now refused where it used to rewrite that weekday's row silently.
  That is the intended cost: the row is not being trained. 3. Fundamentals: every edit still runs
  the shared settle tail on the right row; the three-exercise floor now actually applies to a
  moved session, where before no floor was reached because nothing was found. 4. No floor or
  ceiling changed value or meaning; the floor's SENTENCE changed which day it names. 5. In scope.
  **VERIFIED.** `test:session-ref` (69 checks; 21 mutations, 21 caught): the three sentences
  reproduced, then the resolver over moved / swapped / skipped / rested / ordinary days, every
  spelling the coach's tools use, the real edits through it, and the wiring. `verify:moved-edit`
  (77 checks in all; this entry's are §0-§9; 3 mutations, 3 caught): **moves a session through
  the app's own "What happened?" sheet** — nothing is seeded — then swaps, removes and shortens
  it on screen, reads the saved plan row each time (the session's own row changes; the day's own
  row gains nothing), walks to the floor refusal and checks it names the day on screen and is in
  view, and asks the coach for the same three things three ways (the weekday on screen, no day,
  the session's old weekday) with the model stubbed at the fetch boundary.
  **TO MAKE THAT DRIVABLE, and worth knowing:** the on-screen swap moved out of `App.tsx` into
  `src/lib/screen-swap.ts` (and the ban into `screen-ban.ts`), because no harness page boots
  `App.tsx` and a harness copy would have measured the copy. The harness's fake database gained
  `LIKE`, which the swap's stale-card sweep uses and the fake had never answered — on its first
  run the swap "didn't save" for that reason alone.
  **RE-ANCHORED, deliberately, each on its property:** `test:swap-target` §6 (pinned
  `resolveSwapTarget({` and `dayArg || 'today'` — the mechanism that was the bug; it now asks the
  resolver itself whether an absent day means today), `test:session-edit` (one regex, for the
  `on.say(…)` wrapper), `test:silent-writes` §1 (pinned the inline handler's text; now reads
  `screen-swap.ts` and gained "a swap that changed nothing says so"; 3 mutations, 3 caught).
  **NOT VERIFIED.** Reorder, add, rebuild and volume through the coach on a moved day in a
