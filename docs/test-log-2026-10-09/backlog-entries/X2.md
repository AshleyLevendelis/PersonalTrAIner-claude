- [x] **FINISHING ASKS FIRST, AND THE CARD'S NUMBERS MEAN WHAT THEY SAY — BUILT 9 Oct 2026
  (tester's M12 check, L29, L15, and two leftovers from the cardio entry).** The tester: *"Finish
  session ends at 9 of 24 sets without asking"*; *"80m · 710kg · 7/9: the 9 leaves out the exercise
  I added, and the 80 minutes includes the outage"*; 30 kg in each hand counted as 30.
  **WHAT WAS WRONG.** Finish called `finishSession()` on the tap. The summary's fraction counted
  every logged set on top (planned, extra rows, off-plan lifts) over planned sets only underneath.
  Duration was the wall clock from start to the Finish tap. Volume multiplied the typed number by
  the reps, and the app asks for a dumbbell pair "per hand".
  **WHAT IS BUILT.**
  - **The question before finishing** — the sheet `docs/LAYOUT-DESIGN.md` §3.7 drew and nobody
    built (its "partial variant lists the unlogged remainder ... without judgment"): *"7 of 9 sets
    done — finish anyway?"*, what is still to do per exercise, **Keep going** / **Finish**. Asked
    only when planned sets remain and something has been logged; never when every planned set is
    done; never with nothing logged (the line under the button already says what Finish does then).
    Loaded on the tap (`FinishCheckSheet`, lazy). "Keep going" writes nothing.
  - **The fraction** is planned sets done over planned sets, and anything beyond the plan is beside
    it: the tile reads *"7/9"*, *"Planned sets"*, and on its own line *"+1 extra"*. An extra row on
    a planned exercise is an extra, not a tenth of nine. Found by the driver on the way: a set
    matched to its planned exercise by NAME (a row with no exercise id) was counted under that
    exercise AND again as off-plan work — invisible while extras were folded into one total,
    "20/20 · +19 extra" once they were shown. Fixed, with a check.
  - **Training time**, labelled as that, and the SAME figure written to the session row, so the
    card and history agree (history read the server's own `finished_at − started_at`).
  - **Volume counts both hands** for a dumbbell pair, on the finish card and in history
    (`setVolumeKg`, one function).
  - Finishing with only cardio logged: **"No sets logged — your skipping rope is saved."** (title
    "No sets logged"), then the existing sentence that the day stays open.
  - The sync badge: **"2 sets waiting to send"** (it read "Saved Offline (2 sets queued)");
    "Offline" when nothing is queued.
  - History shows a session's minutes only once it was finished ("not finished" otherwise) — the
    row's default 45 was being printed as if measured.
  Files: `session-derive.ts`, `coach-voice.ts`, `daily-tracking.ts` (`markSessionCompleted` takes
  the minutes), `useActiveSession.tsx`, `exercise-history.ts`, `TodayPanel.tsx`, new
  `FinishCheckSheet.tsx`, `SessionSummaryDialog.tsx`, `SessionHistoryDialog.tsx`,
  `OfflineStatusIndicator.tsx`.
  **DECIDED, AND BY WHOM.**
  - *Ask before finishing with sets left* — **decided unprompted, reversible** (the tracer's owner
    question 1, option a, as the brief instructed; it is what the layout design already drew).
  - *What "duration" measures* — **decided as a CSCS.** From the session's start (the Start tap, or
    the first set, whichever came first) to its LAST SET, adding the gaps between one logged set and
    the next, **no single gap counting for more than ten minutes**; at least one minute once a set
    exists. Basis: session time is work plus prescribed rest; the longest rest the plan prescribes
    is five minutes, and a set plus a change of kit on top fits inside ten — beyond that is an
    interruption (a dead connection, a phone call), not training. Time after the last set is not
    lifting time; cardio has its own line. With no set timestamps at all it falls back to the
    clock, start to finish.
  - *Volume for a pair of dumbbells* — **decided as a CSCS.** BACKLOG's "HALF THE WEIGHTS IN A PLAN
    SAID THE WRONG THING" ruling (Ashley's "14kg per hand") was read first: it settles what the
    number is CALLED and where, and says nothing about volume. Volume load is sets × reps × load
    lifted, so a pair counts both hands; the engine already doubles a per-hand load back wherever
    it compares total work (`load-prescription.ts`). Doubled only for the catalogue's per-hand
    lifts; one side at a time is counted as logged; an unknown name is never doubled on a guess.
    **Personal bests and progression are untouched** — they compare a hand with a hand (pinned).
  - *"No sets logged — your walk is saved"* and *the badge's words* — **decided unprompted,
    reversible** (X1's owner questions 1b and 3a, as the brief instructed).
  **CSCS REVIEW.** (1) Training effect: nothing prescribed changes — no exercise, load, set, rep,
  rest or order. (2) Takes away: the extra-set count is no longer hidden inside the fraction; no
  information is lost. (3) Fundamentals: untouched. (4) **Three figures are redefined, and each
  says so on screen or here**: the fraction (planned over planned), Duration → "Training time",
  and Volume (a dumbbell day's figure doubles). None feeds a prescription: progression reads sets
  and reps, not session volume. (5) In scope.
  **RE-ANCHORED, deliberately:** `test:session-derive` §20 ("setsCompleted counts every logged set
  incl. off-plan" → planned sets done, with the extra beside it; and a check that its wall-clock
  duration is the no-timestamps fallback). X1's `verify:cardio-shows` 3a (it now answers the
  finish question), 3g (the tile's label) and 4e ("1 sets" → "1 set").

  on the harness plan that has a dumbbell pair): the sheet and its numbers, "Keep going" changing

- [x] **HISTORY LISTS THE WORKOUTS, AND THE STREAK COUNTS PLANNED SESSIONS ON THE DAY THEY WERE
  DONE — BUILT 9 Oct 2026 (tester's M15, M30, M16's streak half, M31).** The tester, after two
  workouts: *"5 sessions · 7 PRs. One entry is 'moved · 2026-10-10', a future date. Friday's is
  titled 'training · 2026-10-09' while Thursday's is 'Thursday · 2026-10-08'"*; and *"Streak says
  '2 days' on both days."*
  **WHAT WAS WRONG.** (1) Marking a day rest / moved / missed / swapped stores that note as a row
  in `workout_sessions`, and history listed every row. (2) The streak asked "is this WEEKDAY a
  training day?" and nothing else. Reproduced first in a gate from the tracer's four replayed rows
  (old rule 1 / 2 / 2 / 1).
  **WHAT IS BUILT.**
  - History lists a row only when it has a working set in it (a row whose sets could not be READ
    stays, saying so). A day note is not a session; a session opened and never logged is not one.
    A day swapped for football is listed once, as the activity it was. Titles come from the date
    (`sessionTitle`), which every row has. "N sessions" on Tools counts through the same function.
    "1 set", not "1 sets".
  - The streak is built per DATE (`buildStreakDays` in `streak.ts`) with the resolver every screen
    uses, `sessionForDate`, reading every day note in the window in one query.
  **DECIDED AS A CSCS — the unit of consistency is the planned session, on the date it ran:**
  - a session moved to another day counts where it was done; the day it left is neither a miss nor
    a spent make-up token (the move card already promised "won't count as missed, and it won't
    count against your week"). Two moved sessions in a week, both done, no longer break the streak;
  - nothing before the plan began counts or breaks;
  - a day swapped for another activity KEEPS the streak without being claimed as the planned
    session done — unless she trained anyway;
  - a planned day counts when anything was logged on it, as before (cardio IS the session on an
    activity-shaped plan). The one-miss-a-week token and "today is not a miss yet" are unchanged.
  Basis: adherence is measured against what was programmed. Moving a session inside the week is
  ordinary scheduling, not a missed session; other sport is training load but not the prescribed
  stimulus, so it protects the run without scoring as the session.
  **Decided unprompted, reversible** (the owner question's default): still a "streak", in sessions
  — **"2 sessions in a row"** on Home, in the coach's milestone line and in the note handed to the
  coach.
  **CSCS REVIEW.** (1) Nothing prescribed changes. (2) Takes away: a back-dated activity and a
  swapped day no longer add to the count. (3) Fundamentals untouched. (4) **The streak is
  redefined, and the week's consistency score and session pace move with it** (they read the same
  per-day list): a moved-away day is no longer "scheduled", the day it landed on is. That is the
  intent and matches the move card; it is a change in what three numbers measure. (5) In scope.
  **VERIFIED.** `test:history-streak` (39 checks): seen failing on the old code ("it listed all
  nine rows"), 16 mutations — 15 caught, 1 equivalent (a second "moved away" test that the resolver
  already answers; the redundant clause was deleted rather than given a check). Three were MISSED
  on the first pass and each led to a better fixture: plan weeks now run from the fixture's own
  start, and "today is not a miss" is checked in a week whose token is already spent.
  `verify:history-streak` (15 checks): Home's pill, history's rows and titles, Tools' count, and
  the streak moving after today's set. 4 mutations, 4 caught — one only after the fixture gained a
  second completed move in one plan week (old rule and new had both said 4). Screenshot read: Home.
  **RE-ANCHORED, deliberately:** `test:cardio-reader` (it counted the swapped day's note as a
  lifting session: 2 → 1 of 4, and the Tools count now goes through `countSessions`);
  `test:local-dates` §4 (the streak's date walk moved into `streak.ts`; same property — local
  calendar dates, never fixed milliseconds).
  **NOT CHANGED, AND NAMED (out of bounds for this lane):**
  - The phone notification still says "N days in a row" (`coach-voice.ts` `notification`, whose twin
    is `supabase/functions/_shared/coach-moments.ts`; the two are held in step) and chat-gemini's
    prompt still labels the figure "CURRENT STREAK: N day(s)". Both need the unit changed in a pass
    that may edit the edge functions (then `chat-gemini` and `coach-reach-out` deploys).
  - The day menu still offers "I missed it" / "I did something else" on days before the plan began
    (the tracer's fix list; it is the What-happened sheet). Such an entry no longer scores.
  - A chosen rest on a planned day is still a miss under the token rule, as before (the tracer
    suggested making it transparent; not in this brief, and it is a real question).
  - `block-consistency.ts` still treats any `workout_sessions` row as attendance (the tracer's
    flag). Same blind spot, different reader.
  - The streak still reads cardio from the server only; a cardio log that has not synced does not
    count until it does (X1's note stands).

- [x] **A FIRST LOG IS A BASELINE, NOT A PERSONAL BEST; A RECORD CARRIES ITS UNIT INTO EVERY
  SENTENCE — BUILT 9 Oct 2026 (tester's M12 cause B, L9, M16's PR half, L32's "at 0kg").** The
  tester: five "New PRs" on a first session, all first-ever logs; three warm-up moves and no loaded
  lift under Home's "Recent PRs"; "7 PRs" after two workouts; *"New PR this week: Standing Band Hip
  Abduction at 0kg"*; *"romanian deadlifts from 16 kg"* after 30 was logged.
  **RULINGS CHECKED FIRST.** BACKLOG holds three on personal bests — 16 Sep (bodyweight record is
  most reps in one set; added weight once a belt goes on), 17 Sep (an estimated best shows the whole
  set), 19 Sep (a drop is not a PR). All are about WHAT the record is. None says whether a first
  log is one; `SetGrid.tsx` recorded it as an open question. All three are untouched.
  **DECIDED AS A CSCS: a personal best is an improvement on an earlier performance of the same
  kind.**
  - A first-ever log is a baseline. So is the first set under a belt (no earlier belt set to beat)
    and the first loaded set of a lift only ever done unloaded.
  - A set is measured against the record from BEFORE its day — never against the session's own
    earlier sets (the live cache already held them, so set 2 of a first session "beat" set 1).
  - Movement prep (the catalogue's `primer` tier) and cardio machines hold no record at all,
    excluded where the records are built, so the badge, the finish card, Home, Tools and the
    coach's context all agree.
  - A drop cannot take a best on the finish card either — the NINTH place (CLAUDE.md lists eight).
  - Bodyweight reps records remain personal bests (Ashley, 16 Sep). On Home a loaded lift is listed
    before one, the bigger improvement first, one line per lift, each with its unit.
  Basis: a record that fires on turning up teaches that attendance is progress and makes the real
  one worthless; movement prep is dosed to prepare, not to be beaten.
  **Decided unprompted, reversible** (the owner question's default): on a first log the app says one
  quiet line under the set — *"First time logged — this is your baseline"* — and nothing else.
  **WHAT ELSE IS BUILT.** "N PRs" on Tools and Home's "Recent PRs" come from the list of records
  actually beaten (`getRecordsBeaten`); Home and Tools re-read the records first — they ran one set
  behind, and the set left out was the session's last (found by the driver, not by reading). One
  phrase (`recordPhrase`) builds "X at 13 reps / 35kg / +10kg" for the Home tip, both coach nudges
  and the text handed to the coach; the shape they are given has no bare `weightKg` left to print.
  Home's lift line (`leadLiftPhrase`): the catalogue's name (three of the eight short-name keys
  matched nothing), the one formatter's unit ("16kg per hand"), what was LIFTED once it has been,
  and nothing about a lift a finished session never logged. The exercise's own PR list
  (`derivePRHistory`) follows the same baseline rule.
  **CSCS REVIEW.** (1) Training effect: none — no prescription reads the PR list (progression reads
  sets and reps). (2) Takes away: the trophy on a first log, and every record for movement prep.
  (3) Fundamentals untouched. (4) **"PR" is redefined**: counts and lists before 9 Oct are not
  comparable. Checked that nothing uses the PR cache as a prescription input (`goal-progress` reads
  the all-time max, which is unchanged for lifts; a goal set on a primer would now read no value).
  (5) In scope.
  **VERIFIED.** `test:what-a-pr-is` (52 checks; the tester's Thursday as its fixture), 17 mutations,
  17 caught. `verify:what-a-pr-is` (25 checks): a first session with no trophy, the baseline line,
  an empty PR list, "0 PRs", Home's lift line quoting the 22.5 that was lifted; then with last
  week's sets seeded, the trophy on the set that beat them and one PR on the card, Home and Tools.
  5 mutations, 5 caught. Screenshots read. **NOT VERIFIED:** whether the coach SAYS the right thing
  (model behaviour); the estimate-only best ("95kg × 8") is not driven on a screen.
  **RE-ANCHORED, deliberately:** `test:bodyweight-progress` §3-5 and §8 (first set = PR; now asked
  of somebody with a history and asserted the other way for a first log), `test:exercise-history`
  §3 (3 moments → 2), `test:tools-grid` (the count's source), the `test:coach-nudge` and
  `test:dashboard` fixtures (the record's kind travels with it), and `verify:bodyweight-progress`'s
  fixture (a belt record now has an earlier one to beat).

- [x] **A SESSION STARTS THE SAME WAY WHICHEVER WAY IT STARTS; THE REST BAR READS WHOLE AND LEAVES
  WITH THE SESSION — BUILT 9 Oct 2026 (tester's M7, M12 cause A, M30's titles, L16).** The tester:
  *"'Session running · 0:00' only happens when a session is started by ticking a set"*; every lift
  a "New PR" on that session; "training" against "Thursday" in history; *"'Rest complete — re…' is
  cut off and stays up after the session is finished."*
  **WHAT WAS WRONG.** The Start button and the first ticked set each wrote their own patch. The
  tick wrote the start time to storage and never to the screen's state (the dock's clock reads the
  state), and took no personal-best baseline. The button created the session row before any set
  existed, with no day and no week, and nothing corrected it. And ANY note saved to the record — a
  typed digit, "anything feeling tight?", an added row — stored `running` with a start time of that
  keystroke. Finish never cleared the rest.
  **WHAT IS BUILT.** One function, `sessionStartStamp`, writes what a start writes (running, the
  start time, the record each lift stood at before today) and both paths call it; the tick also
  hands the screen its start time. The record "before today" is DERIVED from the sets by day
  (`getPRBaseline`), so the finish card cannot depend on how the session was opened — the stamped
  copy is only the fallback for a phone that never read the sets. Start workout tells the row its
  day and week; a row with no day gets it filled, one with a day is never renamed. A note is
  `idle`, not `running`. Finish clears the rest in state and in storage, on both ways out. The
  overrun bar is two short lines — "Rest complete" / "Ready for set 3?" — instead of one truncated
  sentence.
  **Decided unprompted, reversible:** the two-line wording of the rest bar (same words, split).
  **CSCS REVIEW:** nothing prescribed changes and nothing that counts as progress changes in this
  entry on its own (the baseline RULE is the entry above).
  **NOT SHOWN, AND SAID:** the dock's clock counting up. The harness has one frozen clock, so no
  pill there ever moves, on either path. What is checked is the thing it counts from — the dock is
  handed a start time the moment a set is ticked — plus the stamp in a logic gate.
  Harness, off by default: the app's real dock mounts behind `?dock=1`; a driver may seed rows
  through `window.__seedDb` (input only).
  **VERIFIED.** `test:session-start` (31 checks), 7 mutations — 6 caught, 1 equivalent (the
  update's own "where day is null" filter holds it). `verify:session-start` (28 checks): seen
  failing on the old code (the row's day null on the button path, "running" from a keystroke, the
  rest left in storage after Finish), 6 mutations, 6 caught. Screenshot read: the rest bar.
