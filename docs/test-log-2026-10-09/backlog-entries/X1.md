- [x] **SETS NEVER LOOK LOST WHEN THE CONNECTION DROPS — BUILT 9 Oct 2026 (tester's H20).**
  The tester logged seven sets, the connection dropped for about ten minutes, and the session read
  "0 logged" — for minutes, and again for five seconds after a reload. A pill said "1 thing didn't
  save" and opened "Dumbbell Floor Press · set 4 · TypeError: Failed to fetch" on a pale pink card
  with labels she could not read. Nothing had been lost.
  **WHAT WAS WRONG — each reproduced before it was fixed.**
  1. A read that failed answered "nothing logged". The Supabase client does not throw on a dead
     network; it resolves with an error, and `getSetsForDate` looked at `data` alone.
  2. A set that had synced had no copy on the phone, so there was nothing to fall back on.
  3. Every tick re-read the day, so a tick on a dead connection WIPED the sets above it.
  4. Loading, failed and empty were the same pixels ("0 logged").
  5. A dead connection counted toward giving up: after five tries (about a minute) a perfectly good
     set was filed under "didn't save" and then waited for a person to tap Retry — and left the
     grid while it waited.
  6. The card printed the browser's error text, in a light-mode colour pair that never switched
     (`dark:` classes; nothing in this app sets that class). Measured on screen: 3.1:1.
  The tracer's report had all of this. One thing it did not: the read can be ANSWERED before a
  set saves and ARRIVE after it, which would have shown the set un-logged and overwritten the
  phone's copy. Found while building the copy; a held-response case in the gate pins it.
  **WHAT IS BUILT.**
  - `readSetsForDate` says whether the server answered (`source: 'server' | 'cache'`) and whether
    the phone has ever had a full answer for the day. The cardio reader has the same shape.
  - The phone keeps its own copy of each day: the last answer the server gave, plus every set that
    has synced since (copied BEFORE it leaves the queue). A read that fails answers from it.
    Ten days kept; a successful read always replaces it.
  - The session is drawn from that copy at once — before the read returns, and when it never does.
    The client retries a dead read three times, about seven seconds; that was the "0 logged" after
    a reload.
  - A set waiting on a connection stays on the grid and says "on this phone, waiting to send". A
    set the server refused stays on the grid, says "didn't save", and has its own **Retry**;
    re-entering or deleting it clears the refusal.
  - A dead connection never gives up on a set, or on a cardio log. It waits and sends itself. When
    a read finds the server again, what was waiting is sent at once rather than at the queue's
    next backoff (up to a minute).
  - Under the session title, only while the read is failing: **"Reconnecting — your sets are
    safe."** When the phone has never managed to read the day it says instead: "Reconnecting —
    can't check today's sets yet. Anything you log now is kept on this phone." A row that cannot
    count says "checking what's logged…" rather than "0 logged".
  - The "Didn't save" card: "There was no connection when this was saved." or "The app couldn't
    save this.", and "Still saved on this device, but not in your history yet." (the cardio
    notice's own sentence). Theme colours throughout. Measured on screen, dark and light: every
    line 6.4:1 or better.
  Files: `set-log-store.ts`, `cardio-log-store.ts`, new `connection-error.ts`, `queue-health.ts`,
  `coach-voice.ts` (the sentences), `types.ts` (`syncStatus` on a set row — never a column),
  `useActiveSession.tsx` (`loadState`, `setsKnown`, `retrySet`), `SetGrid.tsx`, `ExerciseRow.tsx`,
  `TodayPanel.tsx`, `OfflineStatusIndicator.tsx`. Harness: `fake-supabase.ts` can now fail the way
  the real client does (`__netDown`, `?netdown=1`), and `real.tsx` mounts the sync badge as App does.
  **DECIDED, AND BY WHOM.**
  - *The sentences above* — decided unprompted, reversible. "Reconnecting — your sets are safe" is
    the tester's own wording and is only shown when it is TRUE: the rows on screen are held on the
    phone or confirmed by the server. Each is one string in `coach-voice.ts`.
  - *The badge's "Saved Offline (n sets queued)" and "Syncing logs..." are unchanged* (colours
    only). They are jargon by the app's own standard; left for Ashley rather than rewritten here.
  - *Not a coaching change:* the readers that decide next week's weight (progression, calibration,
    finishing) still leave out a set the server refused, as they always did. Showing one on the
    grid is a display fix. They do now fall back to the phone's copy when a read fails, which is
    the same data the server would have given.
  **CSCS REVIEW:** nothing prescribed changes and nothing that counts as progress changes; the one
  place it could have (refused sets reaching progression) was deliberately closed and is pinned by
  a check ("the plain array read leaves it out").
  **VERIFIED.** `test:sets-never-lost` (63 checks; a fake Supabase whose reads RETURN errors, with
  the browser still "online"): seen failing on the old code (43 of 51), 19 mutations, 19 caught.
  `verify:sets-reconnect` (42 checks, real Chromium): seen failing on the old code — a tick on a
  dead connection un-logged the set above it and a reload drew "0 logged" — 9 mutations, 9 caught.
  Three mutations were MISSED on the first pass and each got a check that now catches it: a cardio
  log that synced with no read after it; the send-at-once on reconnect; and giving up on a dead
  connection as seen on screen (the driver now flaps the signal six times). One mechanism that
  could not be pinned on its own (re-reading when a waiting set gets through) was removed rather
  than left untested. Screenshots read: outage, reload, the card in dark and light.
  **NOT VERIFIED / NOT DONE.**
  - A real phone on a real bad connection, and the real client's seven-second failure (the harness
    uses six). The "Syncing logs..." badge and the green "all synced" card were restyled and not
    seen in a screenshot.
  - Reconnecting AFTER a reload is not driven: the harness's server lives in the page and starts
    empty on each load. Reconnection is driven on the page that logged the sets, and the reload on
    a dead connection; the logic gate covers the combination.
  - **THE SAME GIVE-UP RULE IS STILL IN THE WATER AND SHOPPING QUEUES** (`water-store.ts:78`,
    `grocery-store.ts:160`): no error code means "network", and network counts toward five tries.
    A glass of water logged on a dead connection is filed under "didn't save" after about a minute.
    Not fixed here (outside the Exercise tab); the card will at least say "There was no connection
    when this was saved." about it.
  - Finishing a session on a dead connection still waits out the read (about seven seconds) before
    its card opens, and Home still waits for the first read to settle before it draws. Both as
    before; neither is worse.
