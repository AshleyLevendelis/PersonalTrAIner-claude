## Why the drop-index migration is not optional, and is not only about drops

`20260919160000` REPLACES the `unique_set_per_session` constraint with one that
includes `drop_index`. Both the browser client and `chat-gemini` name that
constraint by column list when they upsert a set.

Until the migration runs, a drop set is saved on the device, shown on the card,
and held in the offline queue rather than written over its parent — it syncs
itself once the migration lands.

**The order matters in one direction only.** Both writers were built to work on
BOTH sides of the migration: they try the new conflict target and fall back to
the old one on 42P10 alone. So neither order breaks anything. What WOULD have
broken — and is the reason this is called out — is deploying the OLD
`chat-gemini` after running the migration: the old one names only the old
constraint, matches no unique index, and **every set the coach logs fails**.
So: if you run the migration, deploy `chat-gemini` too.
