# Full app audit — 29 August 2026

## How this was done

I went through the app the way a user does: every screen, every control, every
change a person can make afterwards, and then every way each of those can go
wrong. Then I went through the code underneath looking specifically for the
failure this app keeps producing — **the app says it did something, and it
didn't**.

**Covered:** 5 tabs, 27 onboarding questions, 22 coach tools, ~70 screens and
dialogs, 179 source files (~56,500 lines), 4 server functions, 48 database
migrations, 93 automated checks.

**Evidence labels.** Every finding says how I know it:

| Label | Meaning |
|---|---|
| **Measured** | I ran the app's real code and it produced the number quoted. |
| **Proven** | I read the whole path; the code cannot behave another way. |
| **Observed** | From the built output, the configuration, or the database schema. |

**What I could not do.** This machine cannot reach the database, so nothing
here was tested against a live account with real data. That limit is stated
wherever it matters, and I have not called anything verified that wasn't.

---

## The eight things that matter most

1. **Anyone can read, change or delete every user's data.** All 28 tables are
   open to anonymous access. That includes weight history, injuries,
   allergies and every chat transcript.
2. **There is no account.** Identity is one value in the browser's storage.
   Clear it and the account is gone permanently, with no recovery and no way
   to use a second device.
3. **Changing anything in Profile changes nothing else.** Add a nut allergy
   and today's meals still contain peanut butter. Add an injury and the plan
   keeps prescribing the movement that hurts.
4. **The "foods to avoid" list catches 8% of what people mean.** Typing
   "mushrooms" doesn't match "mushroom" — the field's own example fails.
5. **Typing an injury into Profile does nothing.** Only 8 exact lowercase
   codes work. "Lower back", the app's own suggested example, is ignored.
6. **A coach suggestion older than 10 minutes has a dead Confirm button** —
   no message, no error, nothing happens at all.
7. **The coach refuses three injuries it can actually handle.** Hips, ankles
   and elbows work in the plan engine; the deployed coach still says it can't.
8. **In the gym, the screen sleeps and the rest timer can't reach you.** No
   screen wake-lock, no notifications, and on iPhone no vibration at all.

# 1. Data, privacy and identity

## 1.1 Every table is open to anyone — **Critical**

**Measured.** All **112 of 112** security policies across **28 tables** are
written as `TO anon ... USING (true)` — anonymous, unconditional, full read,
write and delete. The tables include `fitness_profiles`, `daily_metrics`
(weight history), `user_facts` (injuries, allergies, food rules),
`chat_messages`, `exercise_set_logs` and `meal_events`.

The key that unlocks this ships inside the app's JavaScript, because it has
to — that is how this kind of setup works. So the practical position is:
anyone who opens the app in a browser, opens developer tools and copies one
string can then download every user's records, or delete them.

**This was a deliberate choice, and it made sense at the time.** The
migration that set the pattern says so in as many words: *"anon +
authenticated full CRUD (single-tenant, no sign-in)."* For an app with one
user — you — that is a reasonable trade. It stopped being reasonable the
moment other people started using it, and the app has live users now.

What is exposed is not just fitness data. Weight, injuries and allergies are
health information. Under UK GDPR that is special-category personal data, and
"anyone with a public key can download all of it" is not a defensible
position for it.

**What fixing it means.** This is not a one-line change. It needs real
sign-in (Supabase has this built in), then rewriting all 112 policies to
`profile_id = auth.uid()`, then a migration that attaches every existing row
to an account. Realistically a few days of work, and it must be done before
any wider launch. Section 12 has a suggested sequencing.

## 1.2 There is no account — **Critical**

**Proven.** Identity is a single browser-storage entry holding a profile ID
(`App.tsx:294`). There is no sign-in, no email, no password, no recovery.

What follows from that:

- **Clearing browser data deletes the account.** Not the data in the
  database — that stays forever, orphaned — but the user's only route back to
  it. There is no "sign in again".
- **A second device starts from scratch.** Phone and laptop are two different
  people as far as the app is concerned.
- **On iPhone, Safari can throw the account away on its own.** Safari clears
  script-written storage for sites the user hasn't opened in about seven days,
  unless the site has been added to the Home Screen as an app. This app cannot
  be added to the Home Screen (§9.1). So a user who takes a fortnight off can
  come back to a blank app with no explanation and no way to recover.

That last point is the one I would worry about most, because it hits exactly
the user who most needs the app to still be there when they come back.

## 1.3 The server functions are protected by the same public key — **High**

**Observed.** There is no `config.toml`, so the four functions run with the
default setting: a valid key required. The only key is the public one in the
app bundle. So anyone holding it can call `chat-gemini` in a loop. There is no
rate limit, per-user quota or spend cap anywhere in the four functions.

The exposure is a bill, not data. But it is an uncapped bill on your account.

## 1.4 There is no way to delete your data, and no way to export it — **High**

**Proven.** "New Plan" clears the local browser state and starts fresh — it
never deletes anything from the database. Every profile, weigh-in, chat
message and logged set from before it stays there permanently, now
unreachable from the app.

There is no "delete my account", no "download my data", and no deletion path
of any kind. Those are both GDPR obligations once you have users who aren't
you, and neither exists.

# 2. Changes that don't take effect

This is the family Ashley found with the almond butter, and it is broader than
that one case. The Profile screen has **22 editable fields**. I checked what
each one actually changes.

## 2.1 No Profile edit triggers anything — **High (safety-adjacent)**

**Measured** — 11 checks, all failing:

```
Does anything re-check an already-generated meal against the profile?
  App.tsx                 no
  NutritionDisplay.tsx    no
  MealPlan.tsx            no
  Dashboard.tsx           no

Does changing a setting trigger a rebuild?
  App.tsx has 5 effects. None watches dietary_preferences, injuries,
  equipment, or training days.

Does the Profile screen itself trigger anything?
  meal regeneration after a diet edit     no
  plan rebuild after an injury edit       no
  macro recompute after a weight edit     no
```

The code says so itself, at `ProfileScreen.tsx:374`: *"Editing a field here
does NOT recompute macros/targets... live target recalculation off an
arbitrary field edit is a separate feature."*

Here is what that means per field, and how long it lasts:

| You change | What happens | How long it's wrong |
|---|---|---|
| **A dietary restriction or allergy** | Meals already generated are never re-checked. A new vegetarian keeps seeing chicken; someone who adds "Nut-free" keeps seeing peanut butter. | **Forever**, until they find the Regenerate button themselves |
| **Injuries** | The plan is not rebuilt. The contraindicated exercise stays on the card. | **Forever** |
| **Equipment** | Someone who moves from a gym to home keeps a barbell plan. | **Forever** |
| **Training days** | The schedule keeps the old days. | **Forever** |
| **Meals per day, snacks, cuisines, cooking time, breakfast style** | Meals unchanged. | **Forever** |
| **Weight, age, height, activity level** | Calorie and macro targets stay on the old numbers. | Until the app is next reloaded — this one self-heals |

The app *can* tell that a meal breaks a restriction — I ran its own checker
against a breakfast containing peanut butter with "nut-free" set, and it
rejects it correctly. Enforcement simply only ever runs at the moment a meal
is created, and nothing re-runs it afterwards.

**The allergy case is the one to fix first.** The dietary list includes
twelve "-free" tags — nut, dairy, gluten, egg, soy, shellfish, fish, celery,
mustard, sesame and more. Someone adding one of those after a reaction is not
expressing a preference. They will reasonably read a plan that still shows the
food as the app telling them it is fine.

**What fixing it looks like.** Two separate pieces, and I'd do them in this
order:

1. **Re-check on display.** Every meal shown gets run past the current
   restrictions. Anything that fails is visibly flagged and cannot be logged
   as eaten. Small, cheap, and it closes the safety hole on its own.
2. **Offer to redo.** After a change that invalidates the plan, the app says
   what is now out of date and offers to rebuild — rather than doing it
   silently, which would throw away a plan someone may be mid-week through.

Whether (2) should ever be automatic is a product decision, not a bug fix.
My recommendation is to always ask.

## 2.2 Injuries typed into Profile are ignored — **High (safety-adjacent)**

**Measured.** The Profile injury field is free text. The plan engine only
understands eight exact codes. I ran fourteen realistic entries through the
real matcher:

```
"Lower back"          IGNORED     <- exactly what the field's own placeholder suggests
"lower back"          IGNORED
"knees"               works
"Knees"               IGNORED     <- one capital letter
"shoulder"            IGNORED
"shoulders"           works
"rotator cuff"        IGNORED
"hamstring"           IGNORED
"sciatica"            IGNORED
"tennis elbow"        IGNORED
"plantar fasciitis"   IGNORED
"left knee"           IGNORED
"bad back"            IGNORED
"achilles"            IGNORED

12 of 14 are stored, shown back to the user, and change nothing.
```

The field's placeholder reads *"e.g. Lower back"*. Typing exactly that is
silently discarded. It appears in the list afterwards, so it looks saved.

**This exact problem was already found and fixed for food.** Dietary
restrictions used to be free text; they were changed to a fixed picker so a
user could not type something unenforceable. The comment explaining that fix
sits a few lines above the injury field, which was left as it was.

**The fix is the same fix:** make injuries a picker of the eight things the
app can act on, with free text — if kept at all — clearly marked as a note for
the coach rather than something that changes the plan.

## 2.3 The "foods to avoid" list catches 8% of what it should — **High**

**Measured** against the app's real matcher and its real 333-food database:

```
"nuts"          catches  3/11   (27%)  misses peanut butter, almonds, cashews...
"dairy"         catches  0/30    (0%)  misses milk, cheese, yoghurt, butter, whey
"seafood"       catches  0/11    (0%)  misses salmon, tuna, cod, prawns
"red meat"      catches  0/20    (0%)  misses beef, lamb, steak, mince
"gluten"        catches  2/23    (9%)  misses bread, pasta, oats, couscous
"eggs"          catches  0/4     (0%)  the database says "egg", singular
"onions"        catches  0/4     (0%)  the database says "onion"
"mushrooms"     catches  0/1     (0%)  the database says "mushroom"
"spicy food"    catches  0/6     (0%)
"almond butter" catches  1/3    (33%)  misses almonds, almond milk

OVERALL: 10 of 122 foods the user plainly meant are matched — 8%.
```

The Profile field's own placeholder is *"e.g. mushrooms"*. That example
matches nothing.

The matcher is a plain "does this text appear inside that text" check with no
handling of plurals, categories or synonyms. **The app already owns something
much better** and doesn't use it here — the ingredient resolver that meal
generation relies on handles plurals, word order and aliases:

```
"eggs"        plain match -> 0 foods    the app's own resolver -> "egg"
"onions"      plain match -> 0 foods    the app's own resolver -> "onion"
"mushrooms"   plain match -> 0 foods    the app's own resolver -> "mushroom"
"potatoes"    plain match -> 0 foods    the app's own resolver -> "mashed potato"
"tomatoes"    plain match -> 2 foods    the app's own resolver -> "tomato"
```

**The fix is to route the avoid-list through the resolver the app already
has**, and to add category expansion for the handful of words people actually
use — dairy, nuts, seafood, red meat, gluten. That is a contained change to
one function with a clear test.

A caveat I want to be straight about: my measurement compares typed words
against the food database's names. What the filter actually reads is the
ingredient text the meal generator writes, which is close to those names but
not identical. The plural failures ("egg" vs "eggs") are certain either way;
the exact percentage could move a little.

## 2.4 The coach can't change your schedule or your volume — **Medium**

**Proven.** Two coach abilities exist as declared tools and are wired to
always refuse: changing training days, and adjusting sets. The system prompt
instructs the model not to call them and to say the user should do it
themselves — *"the schedule editor for schedule changes, the swap button or
set-count controls for volume changes."*

Two problems with that:

- The "schedule editor" it points to is the Profile screen's day picker, and
  per §2.1 changing days there rebuilds nothing. The coach is redirecting
  people to a control that doesn't do the thing either.
- "I can't move your Tuesday session" is a strange limitation for something
  presented as a personal trainer. Rescheduling is one of the most ordinary
  things anyone would ask.

This is honestly handled internally — the stubs decline rather than pretend —
so it isn't a lie. It is a hole, and it's in the middle of the product's
central promise.

## 2.5 The coach refuses three injuries it can handle — **High**

**Measured.** The plan engine handles all eight injuries, and each one
measurably changes a plan:

```
lower_back removes 16 exercises      hips   removes 11
knees      removes 17                ankles removes 10
shoulders  removes 18                elbows removes 11
neck       removes 12
wrists     removes 14
```

The deployed coach's injury tools accept only five: `lower_back`, `knees`,
`shoulders`, `neck`, `wrists`. Their descriptions say *"only these 5 have
joint-conflict data"*.

That sentence used to be true. Hips, ankles and elbows were added to the plan
engine — there is a comment recording that they previously "did nothing at
all" and were fixed — and the coach's prompt was never updated to match. So
today a user says "my hip's been bothering me" and the coach tells them it
can't adjust for that, which the app can.

**This is live**, since it's in a deployed server function. It's a
small change — widen two lists from five to eight and update two sentences —
but it needs a deploy of `chat-gemini`, not just a push.

# 3. Things that silently do nothing

Every one of these is the same shape: the action appears to work on screen,
and the write behind it failed with nothing said.

## 3.1 A swap that didn't save still looks swapped — **High**

**Proven** (`App.tsx:1604`). Tapping ⇄ on an exercise updates the screen
first, then saves. If the save fails — no signal, bad connection, server
error — the failure goes to the browser console and nowhere else. The swap
sits there looking applied for the rest of the session and is gone on the
next reload.

The same swap **made through the chat** handles this correctly: it returns a
receipt and the card says "Couldn't apply the swap". Two doors to the same
action, one honest and one not.

## 3.2 Banning an exercise offline does nothing at all — **High**

**Proven** (`App.tsx:1516`). "Never show me this again" writes a memory record
first, with no error handling at all. Offline, that throws, the handler stops
before it changes anything, and **nothing at all happens** — no ban, no error,
no visual change. The user taps and the app ignores them.

If that first write succeeds but the plan save afterwards fails, you get §3.1's
version instead: it looks applied and isn't.

## 3.3 Logging steps offline fails silently — **Medium**

**Proven** (`NutritionDisplay.tsx:163`). No error handling. Offline, the
number never saves and nothing is said. The typed value does stay in the box,
which is the only clue.

## 3.4 Editing what the app remembers about you can silently revert — **Medium**

**Proven** (`ProfileScreen.tsx:293–303`). The three save handlers for
remembered facts, goals and context don't check whether the save worked. On
failure the screen reloads from the database and the edit quietly reverts —
no error, no explanation. Better than lying, but a user who corrects something
the coach believes about them has no way to know the correction didn't stick.

## 3.5 Four of five offline queues can lose data with nothing shown — **High**

**Measured.** The app queues writes locally and retries — a good design. Five
things use it: logged sets, water, grocery items, cardio logs and meal events.
Each gives up after five attempts and moves the item to a "dead letter" list.

**Only logged sets have a screen that shows those.** The offline indicator
subscribes to the set queue alone. Water, grocery, cardio and meal events can
each exhaust their retries and be permanently dropped with **no indicator
anywhere in the app, on any screen**.

The fix is mechanical: the indicator should read all five queues, not one.

## 3.6 A coach suggestion older than ten minutes has a dead button — **High**

**Measured**, with a probe against the real code.

Coach suggestions — swap this meal, adapt for this injury — expire after ten
minutes. When you tap Confirm, the app asks to claim the suggestion and gets
one of four answers back. It handles exactly one of them:

```
claim returns "already_resolved" for an expired suggestion    <- proven
claim returns "not_found" if the record is gone               <- proven
claim returns "stale" if you changed the same thing since     <- proven

The chat screen handles "stale"              yes
The chat screen handles "already_resolved"   NO
The chat screen handles "not_found"          NO
```

For the two unhandled answers the code simply stops. The card is not updated,
no message appears, no error shows. **The button does nothing, and keeps doing
nothing however many times it is pressed.**

Ten minutes is short. Read a coach message, get distracted, come back — dead
button. It also survives a reload, because the chat is restored from a local
cache with the card still showing Confirm.

The fix is three lines: mark the card expired and say so.

# 4. Getting the day wrong

## 4.1 The coach uses the wrong day — **Medium**

**Proven** (`ChatAssistant.tsx:692`). Everything the app writes is stamped
with the local calendar date. When the coach is told whether you have trained
today, that one comparison uses the **UTC** date instead.

The two disagree for part of every day in almost every timezone. In the UK
during summer, anything logged between midnight and 1am is filed under
yesterday as far as the coach is concerned. In New York, from 8pm onwards the
coach is already looking at tomorrow and sees no training logged. In Sydney,
it's wrong for the first ten hours of every day.

The user-visible effect is the coach saying you haven't trained when you have,
or the reverse. It's one line.

Two smaller versions of the same thing sit in the streak and block-review
code; both are off-by-one only right at a boundary.

# 5. Nutrition

## 5.1 The shopping list ignores the meals you actually chose — **Medium**

**Proven.** The grocery list is built from the meal *pools* by re-deriving a
week of days. It is never told which meals you actually picked. So if you
swapped tonight's dinner to salmon, the list still shops for the chicken.

The code comment above it says the list "assembles the same days the Nutrition
tab shows" — which is true only until the first swap. The fix is to pass the
picks through.

## 5.2 Meal swaps and dislikes themselves are sound — **Good**

**Measured.** The swap engine correctly refuses to offer an option that
breaks a dietary restriction or contains a disliked food, and it won't let a
named request override a restriction. The almond-butter fix holds: the coach
is now given the actual ingredient list of every meal, from the same reader
that decides whether a meal contains something — so it can't say a food is
absent when it isn't.

## 5.3 Keto and low-carb are collected but not honoured — **Medium**

**Observed.** Both are offered as dietary preferences. Neither changes the
calorie or macro maths — there is no carbohydrate cap anywhere in the
derivation. The coach's own instructions say this plainly and tell it to admit
so if asked, which is the honest handling of a gap. But the app still collects
a preference it can't act on, and shows numbers that aren't keto to someone
who selected keto.

Either build the inverted derivation or stop offering the option.

## 5.4 Steps are typed in by hand — **Improvement**

**Observed.** There is no Health Connect or HealthKit integration; step count
is manual entry, on the Nutrition tab, while the number is displayed on Home.
Someone would have to go looking to find where to enter it.

Asking a person to type their step count every day is a habit almost nobody
sustains, so in practice this number is probably usually empty.

# 6. Exercise

## 6.1 Swaps are correct — **Good**

**Measured** against the real engine:

- With a knee injury, no knee-contraindicated lift is offered.
- On home equipment, no machine is offered — 9 sensible dumbbell options.
- A banned exercise never reappears as a suggestion.
- A swapped-in exercise gets a fresh load rather than inheriting the old one's.

## 6.2 The swap list runs thin — **Improvement**

**Measured.** The catalogue is 158 exercises. For a bodyweight-only user the
alternatives per lift are: squats 2, bench 2, deadlift 4, overhead press 2,
rows 2, pull-ups **1**. With an injury the lists shrink further.

Nothing is broken; the sheet just often has one or two options, which reads as
thin for a paid product. This is a content problem, not a code one.

## 6.3 Set values typed but not yet ticked are lost — **Medium**

**Proven.** The weight and reps you type live only in screen memory until you
tap the tick. Reload, lock the phone long enough for the browser to drop the
tab, or switch apps and come back — and the typed values are gone. Extra set
rows you added are gone too.

Saved sets are safe; the app is careful about those. This is only the
in-progress typing. It happens to be softened by the weight box defaulting to
the prescribed load, but it's still a real annoyance mid-session.

## 6.4 The screen sleeps while you train, and the timer can't reach you — **High**

**Proven.** Three things together:

- **No screen wake-lock anywhere in the app.** During a set, the phone dims
  and locks on its normal schedule. You unlock it between every set.
- **No notifications of any kind.** No permission is ever requested, and
  there is no service worker, so a rest timer that finishes while you are on
  another screen or app cannot tell you.
- **The alert is a sound generated in the page, plus vibration.** Vibration
  does nothing on iPhone — Safari has never supported it. The sound is created
  without a user gesture, which iOS suspends, so it can silently fail too.

The net effect on iPhone: the rest timer finishing may produce nothing at all
unless you are looking at the screen. For a gym app that's a core-experience
problem, not a polish one.

The wake-lock is about ten lines and works on Android Chrome and iOS 16.4+.
Notifications need the PWA work in §9.1.

## 6.5 The plans themselves: measured across 9,216 of them — **Medium**

**Measured.** The plan-quality scorer finished after this audit's first pass
had already been written up. It scores 9,216 profile combinations against six
dimensions. The headline is good:

```
Overall average          11.51 / 12
Plans below the floor         0 / 9216

  Time fit        1.92      Goal alignment  1.96
  Structure       1.97      Primer fit      2.00
  Progression     1.75      Selection       1.90
```

But the rule-frequency table underneath is where the real information is —
these are how often each specific fault appears across those 9,216 plans:

```
progression/frozen_week                 5689   61.7%
selection/worse_implement_than_available 852    9.2%
structure/core_before_main               752    8.2%
selection/load_incoherent                601    6.5%
selection/push_pull_imbalance            530    5.8%
timeFit/time_fit                         458    5.0%
goalAlignment/recovery_volume_not_reduced 455   4.9%
selection/duplicate_movement_family       176    1.9%
```

Three of those are worth acting on:

**Frozen weeks, in 61.7% of plans.** In nearly two thirds of generated plans
there is at least one week where an exercise's load *and* reps are identical
to the week before, and only the effort label changes. It is overwhelmingly
bodyweight work — pull-ups and chin-ups at "4-6 @ bodyweight", week after
week — and light isolation stuck at the same 8kg.

From the user's side: the app tells them they are in week 6 of a progressive
programme, and their pull-ups say exactly what they said in week 5. For
someone whose main lifts are bodyweight, that's most of what they see. The
progression engine has nothing to add for a movement with no external load —
the honest answers are added reps, added range, a harder variation, or added
weight once they can hang it — and right now it does none of them and changes
the label instead.

**Sessions materially shorter than asked for, in 5.0%.** The worst cases are
44% under: someone asks for 90–120 minutes and gets a 50-minute day. Not
dangerous, but it is the app failing to deliver the thing the person
specified, quietly.

**A deload that doesn't deload, in 4.9%.** `recovery_volume_not_reduced` means
a recovery week whose volume wasn't actually cut. That undermines the point of
the week and is a real training-quality issue rather than a cosmetic one.

The rest — a band chosen when a dumbbell was available (9.2%), a plank ordered
before the main lift (8.2%), push/pull imbalance (5.8%) — are polish on an
already-good engine.

Worth being clear about what this section is: the scorer already existed and
already reported all of this. Nothing here is a new discovery about the code.
What's new is reading the frequencies as a product finding rather than as a
gate that passed.

# 7. Onboarding

## 7.1 Twenty-seven questions before anything happens — **Improvement**

**Measured.** 27 questions, 11 of them required. The full list runs from
name, goal and experience through equipment, injuries, lifts, days, session
length, style, cardio, recovery, disliked exercises, age, height, weight,
gender, meals per day, dietary restrictions, foods to avoid, cooking time,
snacks, cuisines and breakfast style.

Every one earns its place in the plan it produces. But a new user answers all
of them before seeing a single thing the app can do. That is a long way to ask
someone to walk on trust, and it is where most drop-off in apps like this
happens.

Worth considering: get to a plan on the required 11, then let the coach pick
up the rest in conversation over the first week — the machinery for that
already exists, since the coach can record any of these mid-chat.

## 7.2 The parts that work well — **Good**

- Progress is saved after every answer, so a crash at question 20 loses
  nothing.
- Body metrics are genuinely optional, and if they're declined the app says
  it has no calorie target rather than inventing one from a guessed weight.
- Wrong-then-corrected answers now re-show the affected question instead of
  quietly corrupting the next one.
- Plan generation is wrapped so a failure anywhere shows an error rather than
  leaving someone on a spinner.

# 8. Accessibility

## 8.1 Sixteen buttons a screen reader can't name — **Medium**

**Measured.** Icon-only buttons with no accessible label:

- **Profile screen — 12.** Every edit, save, cancel and delete control on
  remembered facts, goals and context.
- **Grocery list — 4.** Edit, delete, save, cancel.

A screen-reader user is told "button" with no indication of what it does. The
Profile screen is the one place someone goes to correct what the app believes
about them, which makes it a bad place for this.

Also unlabelled: the two text boxes for editing a grocery item's name and
quantity, which read as two identical anonymous fields.

The fix is one `aria-label` per control.

## 8.2 Text sizes ignore the phone's accessibility setting — **Medium**

**Measured.** 256 font sizes are hard-coded in pixels. Zero use scalable
units. Another 385 use Tailwind's own scale, which does scale.

So a user who has turned up text size in their phone settings gets a mixed
result: some text grows, most doesn't, and the layout is neither the designed
one nor the requested one.

Separately, the app leans very small: about 160 places set text below 12px,
including 13 at 9px and 4 at **8.5px**. Some of that is uppercase with wide
letter-spacing in a muted colour, which is the hardest combination to read.
For an app used at arm's length in a gym, that's optimistic.

## 8.3 Colour contrast is genuinely good — **Good**

**Measured** with the app's own contrast function, across all five themes:

```
                          body text   secondary text
  nightshift                15.80:1          6.10:1
  ember                     16.33:1          7.56:1
  field                     16.15:1          7.85:1
  graphite                  16.48:1          6.75:1
  daylight                  15.75:1          4.91:1
```

The standard for normal text is 4.5:1. Every theme clears it on both, with
room. Worth saying plainly because it is often the thing that's wrong and
here it isn't.

One token (`--text-dim`) sits at 1.5–2.2:1, which would fail badly — but it is
used in exactly one place, as a 5px decorative dot marked hidden from screen
readers. So it is not a text-contrast problem. I checked before reporting it,
because it would have been an easy false alarm.

There is a gap in the safety net though: the automated contrast check only
tests the accent colour against the background, at the 3:1 threshold for large
text. Body and secondary text were never checked. They pass — but by luck
rather than by guard, and a future palette change wouldn't be caught.

# 9. Installing, offline and performance

## 9.1 It can't be installed, and it can't open offline — **High**

**Observed.** There is no web app manifest, no service worker, no app icons
and no Apple mobile web tags. Consequences:

- **No "Add to Home Screen" as a real app.** It can be bookmarked, but it
  opens in the browser with browser chrome, not as an app.
- **No offline shell.** All that careful local-first queueing means writes
  survive a connection drop — but only if the app is already open. Open it
  with no signal and you get the browser's error page.
- **No notifications, ever** (see §6.4).
- **And it makes §1.2 worse:** on iPhone, the seven-day storage eviction that
  can destroy the account applies specifically to sites that *aren't*
  installed to the Home Screen.

A basic manifest plus a caching service worker is a well-trodden day of work
and it improves four separate problems at once.

## 9.2 The favicon 404s on every load — **Low**

**Observed.** `index.html` points at `/favicon.svg`. There is no `public/`
directory and no favicon file anywhere in the repository. Every page load
requests it and gets a 404, and the browser tab shows a blank default icon.

The app has no icon anywhere. One file fixes it.

## 9.3 Everything loads before anything shows — **Medium**

**Measured** from a production build:

```
one JavaScript file    1,527,964 bytes   (437 KB compressed)
one CSS file              95,071 bytes    (16 KB compressed)
```

No code splitting at all. That single file includes the 158-exercise database
(4,199 lines), the plan generator (6,458 lines), the load engine (1,856
lines) and the food database (721 lines) — none of which the Home screen
needs. All of it is parsed before the first screen paints.

On a mid-range phone on mobile data that's a few seconds of blank screen on
first visit. The build itself warns about it.

Splitting the Exercise and Nutrition tabs into separately-loaded chunks is a
standard change and would cut the first load substantially.

The page also blocks on a Google Fonts stylesheet before painting.

# 11. The automated safety net

**Measured.** I ran all 93 checks.

```
90 pass
 3 fail  — none of which is a real regression:
     test:meal-quality    needs the database, unreachable from here
     test:schema-parity   needs the database, unreachable from here
     test:quality         hit MY 15-minute cap, not its own failure
```

I re-ran that third one afterwards without a cap. **It passes**, in
**1,350 seconds — 22 minutes 30 seconds**, scoring 9,216 plan combinations.
So it is not a failure; it is just slow enough that in practice nobody will
run it, and its output (see §6.5) is more interesting than its pass/fail.

The first two are the long-standing pair that can only run with a live
connection. The third is my measurement artefact and I want to be clear it is
not a finding against the app — and it is worth reading its output rather than
only its verdict — see §6.5.

**The 13,967-combination plan audit passes at 100%.** That is a real and
unusual asset: it exercises every plausible combination of goal, experience,
equipment, injuries and days, and checks the resulting plan against a set of
rules. Very little of this size has that.

# 12. What's genuinely good

Worth stating properly, because the list above is long and it isn't the whole
picture.

- **The honesty rules around food are unusual and right.** The coach is
  forbidden from saying a food is absent unless it has actually read an
  ingredient list, and told to say "I can't tell from here" instead. That
  discipline is rare, and it is the direct fix for the almond-butter incident.
- **One reader for "what's in this meal".** The scan that decides whether a
  meal contains something and the text that tells the coach what a meal
  contains are the same function, so they cannot disagree. That was the actual
  root cause and it was fixed at the root.
- **Dietary tags can't drift.** The picker is generated from the enforcement
  list, so it is structurally impossible to offer a restriction the code
  doesn't enforce. The two food databases are held in lockstep by a check that
  compares allergen tags entry by entry.
- **Injury filtering really works.** All eight injuries are mapped and each
  measurably changes a plan — 10 to 18 exercises removed — and there's a check
  that fails if any injury quietly stops doing anything.
- **Exercise swaps are correct**, verified above.
- **Logging is local-first.** Sets, water, grocery and cardio write locally
  first and sync with retries, so a dropped connection mid-session doesn't
  lose the work.
- **Chat failures are honest.** A network failure says so and offers Retry.
  There used to be a path that faked a plausible reply when offline; it's gone.
- **Confirm happens exactly once.** Double-tapping a suggestion can't apply it
  twice — a real atomic claim, not a disabled button.
- **Onboarding survives a crash** at any point.
- **Safe areas are handled properly** on notched phones, and tap targets are
  expanded to 44px in the places that need it.
- **The comments explain the reasoning, not the mechanics.** Most say why a
  thing is the way it is and what went wrong before. That is why this audit
  could go as deep as it did.

# 13. What I'd do, in order

**Before anyone else uses this:**

1. **Sign-in and per-user data access** (§1.1, §1.2). The biggest job here —
   days, not hours — and everything else is less important than it. Sign-in
   also fixes the account-loss problem, because there'd finally be something
   to sign back in to.
2. **Delete-my-data and export-my-data** (§1.4). Small once sign-in exists.
3. **A spend cap on the coach** (§1.3).

**The week after:**

4. **Re-check meals against current restrictions when they're displayed**
   (§2.1). The allergy case. Small, contained, closes a real safety hole.
5. **Make injuries a picker** (§2.2). Same shape as the fix already made for
   food.
6. **Route the avoid-list through the resolver the app already owns** (§2.3).
7. **Fix the dead Confirm button** (§3.6). Three lines.
8. **Widen the coach's injury list from five to eight** (§2.5) — needs a
   `chat-gemini` deploy.
9. **Show failures instead of swallowing them** (§3.1–§3.5): the swap, the
   ban, steps, memory edits, and the four invisible queues.
10. **The UTC date bug** (§4.1). One line.

**Then:**

11. **Offer to rebuild after a change that invalidates the plan** (§2.1). Ask,
    never silently.
12. **Screen wake-lock** (§6.4). Ten lines, immediately noticeable in a gym.
13. **Manifest and service worker** (§9.1) — installable, opens offline,
    notifications become possible, and iPhone storage becomes durable.
14. **Split the bundle** (§9.3).
15. **Label the icon buttons** (§8.1) and move font sizes to scalable units
    (§8.2).
16. **Pass meal picks to the shopping list** (§5.1).
17. **Give bodyweight movements somewhere to progress to** (§6.5). The
    single most common fault in generated plans — 61.7% — and the one a
    user is most likely to notice, because a repeated pull-up prescription
    is visible every single week.
18. **Honour the requested session length** (§6.5) and **actually cut volume
    in a recovery week** (§6.5).

**Decisions that are yours, not fixes:**

- Should the coach be able to move a training day or change your volume?
  (§2.4) Right now it can't, and it's an odd hole in the promise.
- Should keto and low-carb be built properly or removed from the picker?
  (§5.3)
- Is 27 questions the right price of entry? (§7.1)
- Are 1–4 swap options enough, or does the exercise catalogue need widening?
  (§6.2)

# 14. What I couldn't check from here

Stated plainly so the coverage claim is honest:

- **Nothing was run against a live account.** This machine can't reach the
  database. Everything above is from the app's real code run in isolation,
  from reading complete code paths, or from the built output.
- **No live coach conversations.** The four server functions call a model that
  needs network access. I read their logic and their instructions; I did not
  measure what the model actually replies.
- **No real-device testing.** The iPhone-specific claims (vibration, storage
  eviction, suspended audio) come from platform behaviour that is well
  documented and from what the code does or doesn't do — not from a phone in
  my hand.
- **The dislike-matching percentage** is measured against the food database's
  names as a stand-in for the ingredient text meals actually carry. The
  direction and the plural failures are certain; the exact figure could move.

If you want any of these settled properly, the ones worth doing are: a real
onboarding on a phone, one coach conversation about a hip injury, and a
deliberate offline session to watch what the queues do.
